# HPre 1.0.31 First-Frame and Watch-History Design

## Goal

Release HPre 1.0.31 with a materially faster path from a video tap to the first
rendered frame, while limiting watch history to the 50 most recent unique
videos. The release must preserve playback, resume, quality selection,
adaptive playback, comments, related videos, background playback, PiP, URL
expiry recovery, fullscreen sizing, and low RAM/CPU usage.

The release performance gate is a median tap-to-`FIRST_FRAME` improvement of at
least 15 percent over HPre 1.0.30 on the same Android virtual device, ordinary
VOD, network, and cache procedure. At least 10 valid samples are required for
each build.

## Current State

- `NewPipeVideoService` already caches one `ExtractedVideoBundle` and returns
  its `StreamInfo` while the bundle and media URLs remain usable.
- `WatchViewModel` resolves streams before metadata and passes `StreamInfo` to
  `SessionPlayerController`.
- `PlaybackStreamHandoff` transfers `StreamInfo` by an in-process token, but
  the playback service can fall back to another `streamInfo` call when the
  handoff is absent or rejected.
- Playback prewarm has a one-shot `AtomicBoolean` guard. A synchronous failure
  does not reopen that guard, and an idle prewarm connection failure currently
  stops without using the normal bounded reconnect path.
- Home already keeps stale content visible while it revalidates, but
  `HomeFeedStore.load`, serialization, and deserialization run synchronously
  from `HomeViewModel.load` before its network coroutine starts.
- Home recommendation work launches trending and topic-search requests that
  can still occupy extractor/network capacity when the user selects a video.
- `watch_history` already has the composite primary key `(serviceId, videoId)`,
  so an upsert naturally preserves one row per video and moves a rewatched
  video by replacing `watchedTimestamp`.
- Recommendation generation currently reads up to 100 watch-history rows.
- Extractor and playback already share the application `OkHttpClient`,
  connection pool, cookie jar, User-Agent, and connect/read timeouts. Playback
  deliberately removes the total call timeout because a media response may
  remain open for the full playback session.

## Selected Approach

Use targeted cancellation and strengthen the existing playback handoff. Do
not add a global request-priority scheduler, another extractor executor, a
second HTTP client, or speculative video prefetching.

Immediately before navigating to Watch, the source ViewModel cancels its
nonessential active network work. Structured coroutine cancellation then
propagates into the existing extractor cancellation bridge, freeing active
calls and worker threads for the selected video. This covers Home background
revalidation and active Search first-page/pagination work without introducing
new long-lived coordination state.

## Video-Open Data Flow

1. A video selection records the tap timestamp and cancels active background
   Home or Search work before navigation.
2. `WatchViewModel` claims the pending metrics session for the same key, or
   creates a fallback session for direct navigation, then records
   `STREAM_RESOLVE_START` immediately before resolving the stream.
3. `NewPipeVideoService.streamInfo` returns the exact cached `StreamInfo`
   instance when its URLs are usable. A real extractor call occurs only for a
   cache miss, forced refresh, expired URLs, or recovery.
4. `WatchViewModel` records `STREAM_INFO_READY` and passes that exact object to
   `SessionPlayerController.prepare`.
5. `SessionPlayerController` retains the object and places the same reference
   in `PlaybackStreamHandoff` for the matching prepare generation.
6. `HPrePlaybackService` consumes only a handoff whose key and generation
   match. It validates URL usability before preparing. A usable handoff goes
   directly to media-source selection; it must not call `VideoService` again.
7. If the handoff is missing or its URLs are no longer usable, the service may
   ask `VideoService` for stream information. That path must hit the existing
   extraction cache first and perform a real refresh only when the cached URLs
   are invalid.
8. The service records `PLAYER_PREPARE` immediately before the actual
   `ExoPlayer.prepare()` call and records `FIRST_FRAME` from the current
   analytics-listener generation.

Tests will prove object identity across the handoff and prove that the service
fallback does not increase the extraction count while cached URLs are usable.

## Background Request Cancellation

`HomeViewModel` gains a video-selection action that cancels `activeLoadJob`,
increments its generation, and leaves the visible cached feed intact. Any
refresh/loading decoration is cleared so returning to Home does not show a
request that no longer exists.

`SearchViewModel` gains a matching action that cancels active first-page and
pagination jobs while retaining cached results. New typing or an explicit
retry starts fresh work normally.

Navigation callbacks invoke these actions before recording the tap and before
calling `navigate`. Related-video navigation already cancels outgoing Watch
work and keeps that behavior.

Cancellation, rather than pausing and resuming the same provider calls, is
intentional: Home and Search already cache successful results, and restarting
stale low-priority work later is cheaper and simpler than retaining suspended
extractor operations.

## Prewarm Retry

Prewarm remains bounded and uses the existing application-scoped controller.

- If media-source or controller construction throws, the orchestration guard
  returns to the idle state so a later prewarm request can try again.
- An asynchronous controller connection failure during prewarm uses the
  existing bounded backoff, with at most three retry attempts.
- Idle prewarm failures do not publish a playback error because no media was
  requested.
- A real `prepare` switches the controller to normal purpose, resets any
  exhausted prewarm retry budget, and is always allowed to initiate a fresh
  connection attempt.
- Cancellation remains cancellation; it is not swallowed or converted into a
  retry.

This removes the one-failure lockout without adding an unbounded retry loop or
keeping extra threads alive.

## Startup Stream Selection and HTTP Consistency

For ordinary non-live video, startup selection uses a progressive video stream
that already contains audio whenever one is compatible. This avoids manifest
parsing and a second synchronized media request. Merged audio/video, HLS, and
DASH remain available for progressive incompatibility, live/adaptive content,
recovery, and explicit quality selection.

The application continues to pass one shared `OkHttpClient` to extractor,
playback, image loading, update checks, and media probing. Regression tests
will assert shared dispatcher/pool/cookie state, the common User-Agent, and the
same connect/read timeout values. Playback keeps `callTimeout = 0`; applying
the extractor's finite total call timeout to a long-lived media body would
break valid playback. Media-specific method, range, origin, and referrer rules
remain centralized in the existing media request policy and are tested for
progressive, HLS, and DASH profiles.

## Home Cache

`HomeFeedStore.load`, `save`, and `remove` become suspend operations with an
injected IO dispatcher. SharedPreferences access, Base64 work, binary encoding,
and binary decoding all execute inside that IO context.

Home retains its current stale-while-revalidate behavior:

1. Use a fresh in-memory chip entry immediately when available.
2. Otherwise read the disk snapshot on IO and publish it as stale content.
3. Keep that content visible while the selected feed revalidates in the
   background.
4. Replace and persist the feed after a successful response.
5. Preserve stale content and surface the refresh failure inline when the
   background request fails.

A forced pull-to-refresh retains the current list. No Home path prefetches or
extracts batches of video streams. The existing no-op `VideoService.prefetch`
policy remains in force, and obsolete viewport-prefetch plumbing may be
deleted where it has no effect.

## Watch-History Limit

The watch-history limit is 50 unique videos. Search history is unchanged.

`HistoryDao` gains a Room transaction equivalent to the existing search
history write pattern:

1. Upsert the row keyed by `(serviceId, videoId)`.
2. Delete rows outside the newest 50 ordered by `watchedTimestamp DESC`, then
   by stable key columns for timestamp ties.

`DefaultHistoryRepository.recordHistory` calls that transaction while keeping
its existing write mutex, history-enabled check, metadata preservation, and
resume-position policy. The first successful history write after upgrading
also trims any older installation that already contains more than 50 rows.
No Room schema version change is required because only DAO operations change.

`RecommendationRepository.MAX_WATCH_HISTORY_SIGNALS` changes from 100 to 30.
`PlaybackSnapshotStore` is not modified or cleared. History item deletion,
clear-all, disabling history, watched indicators, and resume behavior remain
unchanged.

## Performance Metrics

Metrics retain cumulative elapsed time and add explicit duration records for:

- `STREAM_RESOLVE_START` to `STREAM_INFO_READY`
- `STREAM_INFO_READY` to `PLAYER_PREPARE`
- `PLAYER_PREPARE` to `FIRST_FRAME`

The first segment covers both cache lookup and any required extraction.
Existing `EXTRACTOR_START` and `EXTRACTOR_FINISH` events distinguish an actual
extraction from a cache hit. `PLAYER_PREPARE` moves to the playback service so
it represents the real ExoPlayer call rather than command dispatch from the
ViewModel.

The overall session starts at the UI selection. Direct navigation without a
selection creates a fallback session in Watch. Cancelled or replaced
navigation retires the old session so a later open cannot reuse a stale tap.

Records contain only generation, event/segment, elapsed milliseconds, segment
milliseconds, and coarse source/error category. They must never contain a
content key, title, URL, query string, request headers, cookies, tokens,
response bodies, or raw exception messages.

## Testing

Implementation follows test-driven development. Targeted tests cover:

- one extraction and one `StreamInfo` identity through Watch, controller, and
  playback-service handoff;
- valid cached fallback without another extraction, plus expired-URL refresh;
- prewarm synchronous failure reopening its guard, bounded asynchronous retry,
  and a fresh normal retry after prewarm exhaustion;
- progressive-with-audio startup priority and all fallback/manual/adaptive
  paths;
- Home and Search video selection cancelling background work while retaining
  visible content;
- HomeFeedStore read/write/codec work executing on the injected IO dispatcher;
- stale feed publication before revalidation completion;
- watch-history uniqueness, newest-first ordering, rewatch promotion, and
  trimming 51 rows to 50 in one transaction;
- recommendation history input capped at 30;
- unchanged search-history capacity and operations;
- the three metric segments, tap ownership, stale-session rejection, and
  privacy-safe records.

## Benchmark Gate

Use the available API 35 HPre AVD and a fixed ordinary VOD. Build an isolated
1.0.30 benchmark APK with the same measurement-only tap/segment instrumentation
as the candidate, without any 1.0.31 behavior changes. That artifact is local
benchmark input only and is never published.

For each build, perform a warm-up followed by at least 10 valid opens under the
same app-state, cache, video, AVD, and network procedure. Report each segment,
the total tap-to-`FIRST_FRAME` samples, median, minimum, maximum, failures, and
stream category. The release gate passes only when the candidate total median
is at least 15 percent lower than the 1.0.30 median. Missing or incomparable
samples fail the gate rather than being discarded silently.

## Release

- Base implementation on the latest remote `main`, which already contains the
  merged 1.0.30 work.
- Set `versionCode = 32` and `versionName = "1.0.31"`.
- Add `docs/releases/1.0.31.md` with the verified changes and gates.
- Build the release APK with the existing HPre release key and copy it outside
  the repository as `HPre-v1.0.31-release.apk`.
- Verify package, version, APK signature, signing-certificate continuity, and
  file SHA-256.
- Download the official `HPre-v1.0.30-release.apk` and run the repository's
  static and full install-over gate on a dedicated AVD, preserving the marker
  data required by the release script.
- Push the implementation branch and merge it into `main` only after tests,
  benchmark, signing, and upgrade gates pass.
- Create annotated tag `v1.0.31` at the verified `main` release commit.
- Create the public, non-prerelease GitHub Release `HPre 1.0.31` and attach only
  `HPre-v1.0.31-release.apk`.
- Verify the remote tag, release metadata, exact asset name, nonzero asset
  size, download URL, and published SHA-256 before reporting completion.

No APK, keystore, password, benchmark artifact, device data, or credential is
committed to source control.
