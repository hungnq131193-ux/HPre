# HPre 1.0.11 Startup and Comments Release Design

**Date:** 2026-08-30

**Status:** Approved by user

## Goal

Reduce the median time from tapping a video to its first rendered frame, improve the read-only comments presentation, and release HPre 1.0.11 with the established HPre signing certificate.

The release preserves the playback reliability work in 1.0.10. It does not trade startup time for a higher rebuffer rate or claim a fixed startup time because NewPipe extraction, the upstream provider, and network conditions vary.

## Scope

### Video startup critical path

The measured startup path remains:

```text
VIDEO_OPEN_START
  -> STREAM_INFO_READY
  -> PLAYER_PREPARE
  -> PLAYER_READY
  -> FIRST_FRAME
```

Keep the current uncached Watch ordering in which stream extraction, details extraction, and resume lookup start concurrently and `playerController.prepare()` is dispatched as soon as stream information and the bounded resume lookup are ready.

Related content may continue after prepare because it normally projects the completed short-lived extraction bundle. Comments use a separate upstream endpoint and must no longer start immediately after prepare. Hold the initial comments request until either:

1. the current `ContentKey` reaches player ready; or
2. a two-second fallback expires after prepare dispatch.

The fallback prevents the comments section from waiting indefinitely if a ready callback is lost or playback remains in a recoverable transition. The ready signal and fallback are both bound to the current Watch generation and key. Exactly one path may admit the initial comments request. Navigating to another video cancels the pending gate and prevents stale requests.

Cached comments remain visible immediately and do not enter the gate. Unsupported comments remain empty. Related content and existing cached Watch metadata behavior remain unchanged.

### Extraction bundle cache

Set `VideoExtractionCoordinator`'s default maximum entries to 16. The current value of eight conflicts with the capacity restored for 1.0.10 and reduces reuse when users return to recently opened videos.

Keep the existing 20-second TTL, access-order eviction, single-flight behavior, cancellation semantics, immediate failure removal, and thread safety. Do not add another cache or cache abstraction.

### Playback policy

Preserve the 1.0.10 Media3 load-control values, startup quality policy, source selection, retry, stream recovery, and network timeouts. In particular, do not reduce startup buffer thresholds to manufacture a faster first frame at the cost of rebuffering.

### Comments interface

Redesign `CommentsSection.kt` as the approved open-row layout:

- retain one lazy-list item per comment with the stable `commentId` key;
- show a circular 36 dp avatar using the existing Coil dependency and crop it to fill;
- show a lightweight initial fallback when the avatar URL is absent;
- place author and formatted publication time on the first line;
- place comment text below with readable line height;
- show available like and reply counts as non-interactive metadata;
- separate rows with a subtle divider instead of wrapping each row in a card or surface;
- retain the existing loading, empty, error, retry, and automatic pagination sentinel behavior;
- provide meaningful avatar accessibility descriptions and keep decorative metadata icons hidden from accessibility services.

The domain model does not expose the total comment count, so the header remains `Binh luan`/`Comments` without a fabricated count. Reply content, sorting, voting, author navigation, and comment submission are out of scope. A non-zero `replyCount` is displayed only as metadata and is not presented as an expandable thread.

Use existing localization and number/date-formatting utilities where available. Add only the minimum resource strings needed for metadata and accessibility. Do not add a dependency, animation, nested list, or per-comment surface.

## State and Error Handling

- Stream and details failures retain the existing Watch retry behavior.
- A comments failure remains local to the comments section and cannot replace playback or metadata state.
- The ready gate, fallback, comments job, and in-flight flag are reset or cancelled when the Watch generation changes.
- If ready and fallback race, the existing admission guard and a dedicated pending-gate state ensure one request starts.
- Cached comments bypass the gate and are never replaced by an unnecessary loading state.
- Stale generations cannot publish comments, prepare an obsolete stream, or update the current cache entry.

## Tests

Development follows TDD. Add or update focused tests that prove:

1. the extraction bundle cache default capacity is 16;
2. initial comments do not start before prepare dispatch or before the player-ready gate opens;
3. current-key player ready starts comments exactly once;
4. the two-second fallback starts comments exactly once when ready does not arrive;
5. ready and fallback racing cannot duplicate a request;
6. changing video cancels or invalidates the prior comments gate;
7. cached comments render immediately without another request;
8. the open-row UI displays avatar, avatar fallback, author, time, body, optional likes, and optional reply count;
9. loading, empty, error, retry, and pagination sentinel behavior remains intact;
10. accessibility descriptions and existing Watch ordering remain correct.

Run:

```text
./gradlew test
./gradlew assembleDebug
./gradlew assembleRelease
./gradlew connectedAndroidTest
```

Report `connectedAndroidTest` as unavailable rather than passing when no Android device or emulator is online.

## Device Benchmark

Build debug APKs from the tagged 1.0.10 source and the 1.0.11 candidate source, then compare them on the same physical Android device, same Wi-Fi network, and same representative video set. Perform ten opens per build under equivalent cache conditions and record `VIDEO_OPEN_START` through `FIRST_FRAME` events. Use equivalent build configuration apart from the source revision so debug timing instrumentation is available on both sides.

Use the median tap-to-first-frame duration as the primary comparison. The candidate must improve that median. Separately smoke-test the official signed 1.0.10 release APK and signed 1.0.11 candidate for playback failures and observed rebuffering; the candidate must not regress. Record the device, Android version, network conditions, video set, individual debug-build durations, and median so the result is reproducible. A benchmark or release-build smoke regression blocks release.

## Version, Signing, and Upgrade Gate

Update `app/build.gradle.kts`:

- `versionCode`: 11 to 12;
- `versionName`: 1.0.10 to 1.0.11;
- preserve application ID `com.hpre.app`, release minification, and resource shrinking.

Build with the existing keystore at `C:\Users\HUNG\.android\hpre-release.jks`, alias `hpre`, and credentials already stored outside the repository in the user-level Gradle properties. Never read credentials into logs, copy the keystore, generate a replacement key, or commit signing material.

Rename the verified artifact to `HPre-v1.0.11.apk`. Android build-tool verification must prove:

- APK Signature Scheme v2 is valid;
- package is `com.hpre.app`;
- version name is `1.0.11`;
- version code is `12`;
- signer certificate SHA-256 is `40:D6:29:54:4B:6C:12:01:4A:D0:A0:3B:ED:C2:AF:FE:81:E6:DF:8E:F8:8F:69:3F:76:36:5A:6E:95:D4:9D:47`.

Run `scripts/release/verify-android-upgrade.ps1` with the official 1.0.10 APK as baseline and the signed 1.0.11 APK as candidate. Package, versions, certificate continuity, `adb install -r`, DataStore marker preservation, and the Settings smoke check must pass. Missing device access is reported accurately and blocks public release unless the user explicitly changes the established release gate.

## GitHub Delivery

Work on branch `perf/hpre-1.0.11-startup-comments`. Before each commit, inspect status and diff, run `git diff --check`, and stage only intended files. Keystores, credentials, `local.properties`, build outputs other than the final release asset, benchmark device data containing personal information, and `.superpowers` session files must not be committed.

After all source and local build gates pass:

1. commit and push the branch;
2. create a pull request into `main` and wait for CI/review;
3. do not merge automatically and do not create a release tag before merge;
4. after user-confirmed merge, update and verify local `main` against `origin/main`;
5. create and push annotated tag `v1.0.11` at the verified merged commit;
6. create GitHub Release `HPre v1.0.11` and attach only `HPre-v1.0.11.apk`.

GitHub CLI is not currently installed. Install it through the native package manager if available and use an existing authenticated session. Never place a GitHub token in source, a command argument, shell history, or release notes. If CLI installation or authentication is unavailable, stop before PR or release creation and report the blocker.

## Release Gates

Public release is blocked by any of the following:

- unit, build, instrumentation, or required upgrade test failure;
- candidate median tap-to-first-frame regression against 1.0.10;
- increased playback failures or rebuffering in the benchmark smoke run;
- package, version, signature, or signer mismatch;
- failed install-over or local-data preservation;
- candidate commit not merged into `main`;
- inability to create and verify the GitHub release safely.

## Deliberate Omissions

- No stream prefetch: it can waste data, retain expiring URLs, and complicate cancellation without current intent signals.
- No lower startup buffer: 1.0.10 reliability takes priority over an artificial first-frame reduction.
- No Home/Search refactor: the requested release has no profile proving those screens are bottlenecks.
- No comment replies, sorting, voting, posting, or model/extractor expansion.
- No new cache, telemetry service, benchmark module, image dependency, or UI framework.
