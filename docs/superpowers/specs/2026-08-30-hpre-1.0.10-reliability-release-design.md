# HPre 1.0.10 Reliability Release Design

**Date:** 2026-08-30

**Status:** Approved by user

## Goal

Remove the 1.0.8/1.0.9 runtime regressions that can delay opening a new video, block lifecycle cleanup, increase cache misses, and rebuffer on weak networks. Release the corrected build as HPre 1.0.10 with the established HPre signing certificate.

The release favors stable video startup over a fixed timing target because extraction and first-frame timing depend on the upstream provider and network.

## Scope

### Playback snapshot persistence

`PlaybackSnapshotStore.saveSync()` currently calls `runBlocking { withContext(Dispatchers.IO) { DataStore.edit(...) } }`. This still blocks the calling thread, including `HPrePlaybackService.onDestroy()` and lifecycle cleanup paths.

Replace the synchronous DataStore write with the existing generation-aware asynchronous writer:

- Update the in-memory snapshot under the existing lock before returning.
- Enqueue the DataStore edit on the store IO scope.
- Preserve latest-generation-wins behavior so stale scheduled writes cannot overwrite a newer snapshot or clear.
- Keep persistence failures best-effort and non-fatal, as they are for ordinary snapshot writes.
- Remove `runBlocking` and its imports.

The final snapshot is durable when the scheduled write runs, but service destruction never waits for disk I/O. The current shared app-level store survives the service's local scope, so the enqueue remains valid after the service finishes cleanup.

### Extractor admission

Increase the bounded NewPipe dispatcher to eight workers and a 32-item queue. This absorbs simultaneous Home, Search, Watch, related, and comment-adjacent extraction without returning to an unbounded executor.

The dispatcher keeps its finite queue, thread naming, cancellation behavior, idle core-thread timeout, and rejection policy. Tests will assert the configured worker and queue bounds.

### Cache capacity

Restore the capacities that existed before the 1.0.8 memory reduction:

| Cache | Capacity |
| --- | ---: |
| Watch state | 10 |
| Video extraction bundle | 16 |
| Playback stream handoff | 16 |
| Catalog search | 50 |
| Catalog details metadata | 100 |

TTL, eviction order, cache value semantics, and invalidation behavior remain unchanged. No new cache abstraction or telemetry is added.

### New video startup

Keep Watch's existing critical-path ordering: stream extraction and resume lookup start together, `prepare()` occurs when both resolve, and related/comments remain after prepare.

Harden `SessionPlayerController.prepareWithSpeed()` so a pending prepare starts a MediaController connection when the controller is absent and no connection is running. The connection completion path already drains `pendingCommands`; this repair ensures a new stream cannot remain in an indefinite loading state after controller disposal or a failed prior connection.

Tests will cover a pending prepare issued with no controller, verify one connection attempt is started, and verify the prepared command is delivered after connection. Existing generation checks remain responsible for preventing stale prepare delivery.

### Playback buffer

The 20-second minimum and 50-second maximum buffer predate 1.0.9, so there is no previous configuration to restore. Tune Media3 `DefaultLoadControl` directly:

| Setting | Current | 1.0.10 |
| --- | ---: | ---: |
| Minimum buffer | 20 s | 30 s |
| Maximum buffer | 50 s | 90 s |
| Buffer required to start | 2.5 s | 2.5 s |
| Buffer required after rebuffer | 5 s | 8 s |

Keeping the start threshold at 2.5 seconds avoids deliberately delaying new playback. The larger steady-state and rebuffer thresholds provide more network headroom once playback has begun. Existing source selection, fast-start quality escalation, retry, recovery, and network timeout policies remain unchanged.

## Error Handling

- Snapshot write exceptions remain contained; they do not block, crash, or revive an obsolete snapshot.
- Extractor overload remains bounded by executor rejection instead of growing unbounded work.
- Missing or failed MediaController connections retain existing bounded retry and visible network error behavior.
- Stream, resume, and Watch generation checks continue to cancel or ignore stale requests.

## Tests

Add or update focused unit tests for:

1. final snapshot persistence updates memory immediately and schedules DataStore persistence without blocking the caller;
2. a later generation prevents an earlier scheduled final write from replacing it;
3. extractor executor uses eight workers and a queue capacity of 32;
4. restored cache capacities are configured at their owning sites or exposed constants;
5. a controller-absent prepare begins exactly one connection attempt and delivers the pending command after connection;
6. load-control buffer constants match the 1.0.10 values.

Run `./gradlew test`, `./gradlew assembleDebug`, and `./gradlew assembleRelease`. Run connected tests and the install-over gate when an Android device or emulator is available; otherwise report them as unavailable.

## Version, Signing, and Delivery

- Set `versionCode` to `11` and `versionName` to `1.0.10`.
- Preserve application ID `com.hpre.app`, release minification, and the existing release signing configuration.
- Use only existing `hpreSigning.*` Gradle properties or `HPRE_SIGNING_*` environment variables. Never generate, copy, or commit a keystore or credentials.
- Build the signed APK as `HPre-v1.0.10.apk`.
- Verify APK signature, package, version name/code, and signer SHA-256. Compare the signer against the official `v1.0.9` APK; mismatch blocks delivery.
- Start branch `perf/hpre-1.0.10-reliability` from current `origin/main`, push it, and create a PR into `main`.
- Do not create the tag or GitHub Release before the PR merges.
- After merge, verify `main`, create and push `v1.0.10`, create GitHub Release `HPre v1.0.10`, and attach only the verified signed APK.

## Deliberate Omissions

- No fixed tap-to-first-frame SLA: upstream extraction and network variability make it unreliable without controlled device measurements.
- No unbounded extractor pool or queue: bounded admission avoids memory and upstream overload.
- No timeout/retry rewrite: the demonstrated regressions are lifecycle blocking, restricted admission, reduced cache capacity, and missing connection admission.
- No new cache framework or benchmark module: the existing bounded caches and debug timing remain sufficient for this targeted release.
