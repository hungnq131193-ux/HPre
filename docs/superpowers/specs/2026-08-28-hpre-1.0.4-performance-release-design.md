# HPre 1.0.4 Performance and Release Design

**Date:** 2026-08-28
**Status:** Approved by user

## 1. Goal

Reduce time from video tap to `player.prepare()` and first rendered frame without removing features or replacing HPre's current Kotlin, Compose, Media3, Room, DataStore, OkHttp, Coil, or NewPipeExtractor architecture. Release resulting build as HPre 1.0.4 only after tests, release signing continuity, and available upgrade checks pass.

Primary path:

```text
VIDEO_OPEN_START
  -> STREAM_INFO_READY
  -> PLAYER_PREPARE
  -> PLAYER_READY
  -> FIRST_FRAME
```

## 2. Constraints

- Preserve application ID `com.hpre.app` and all current playback, PiP, background, resume, history, playlist, subscription, search, recommendation, comment, quality, recovery, update-checker, and cache behavior.
- Keep NewPipeExtractor as upstream provider.
- Make small, testable changes. Do not rewrite architecture.
- Do not create or commit a keystore, credentials, `local.properties`, or other secrets.
- Use only existing HPre release signing configuration and certificate.
- Do not push if unit tests, debug build, or release build fail.
- Do not tag or create GitHub Release until release commit is on `main` through user-approved merge.

## 3. Findings

### 3.1 Duplicate extraction

`DefaultExtractorOperations.video()`, `streamInfo()`, and `related()` each independently:

1. resolve the same stream link handler;
2. construct a new stream extractor;
3. call `fetchPage()`;
4. call NewPipe `StreamInfo.getInfo()`;
5. map one projection of the result.

Opening one video can therefore perform three expensive upstream extractions for one `ContentKey`. Existing `RequestCoordinator` cannot remove this duplication because its keys are result-type-specific and the three calls return different types.

### 3.2 Critical-path contention

On an uncached Watch load, details start concurrently with stream extraction, but related and comments are deliberately launched before stream extraction. They contend for NewPipe dispatcher threads, parsing CPU, and the shared OkHttp pool before playback prepare.

Resume and stream already run concurrently on an uncached load. On a `WatchStateCache` hit, resume lookup currently completes before stream extraction starts, serializing local storage ahead of the critical network request.

### 3.3 Existing behavior worth retaining

- `CatalogRepository` caches details for 60 seconds and coalesces same-result requests.
- `WatchStateCache` retains usable details, related videos, and comments for five minutes and renders them without a full-screen spinner.
- Related refresh preserves prior content.
- Resume lookup has a bounded 1.5-second fallback to 0 ms.
- Startup source selection already prefers HLS/DASH, applies a 360p adaptive startup cap, and selects a low progressive rendition when no adaptive manifest exists.
- Coil already shares OkHttp, uses bounded memory/disk caches, decodes RGB565, and disables crossfade.
- Home, Search, Watch, Related, and Comments lazy lists already use stable keys.

No Media3 buffer, network timeout, retry, image, or Compose-list change is justified without further measurement.

### 3.4 Cold-start work

`HPreApplication.onCreate()` collects background-playback preference and calls `createPlayerController()` on the first emission. That instantiates and connects the MediaSession controller even when the user has not opened playback.

## 4. Extraction Bundle

Add a narrowly scoped `ExtractedVideoBundle` containing:

- `VideoDetails`;
- app-model `StreamInfo`;
- provider-related `VideoSummary` items.

`DefaultExtractorOperations` performs one upstream stream-page extraction and maps all three projections from the resulting NewPipe `StreamInfo`. Existing `video()`, `streamInfo()`, and `related()` public service methods remain unchanged and return their projection from the bundle.

This replaces up to three `fetchPage()`/parse operations with one for near-simultaneous consumers of the same key.

## 5. Single-Flight and Short TTL

`NewPipeVideoService` owns extraction sharing because all consumers pass through it, including playback recovery and service restoration.

For each `ContentKey`:

- at most one bundle extraction may run at a time;
- concurrent callers await the same result;
- a waiter cancellation does not cancel upstream while another waiter remains;
- upstream is cancelled when the last waiter leaves;
- success is retained for 20 seconds;
- failure is removed immediately;
- expired success is removed before a new request;
- cache capacity is 16 entries with access-order eviction;
- all in-flight and cache mutation is thread-safe;
- no NewPipe extractor object escapes the operation or remains cached.

The short TTL limits signed stream URL lifetime and memory use. This cache does not replace `CatalogRepository` or `WatchStateCache`: those hold longer-lived UI metadata, while the bundle exists only to collapse one video-open burst.

Use the existing cancellation-safe `RequestCoordinator` pattern where practical, but do not force heterogeneous projections into existing typed keys. A focused bundle coordinator is acceptable if it remains smaller than generalizing repository request types.

Debug builds maintain an in-memory `extractCount[ContentKey]` counter for upstream bundle executions. It must not log URLs, stream query strings, cookies, or personal data.

## 6. Watch Critical Path

For a fresh video:

```text
T=0:
  start bundle-backed stream request
  start bundle-backed details request
  start resume lookup

stream ready:
  await bounded resume result
  call playerController.prepare()

after prepare dispatch:
  start related
  start comments
```

Details may publish before or after prepare. Because details and stream share the bundle, starting both does not duplicate upstream extraction.

Related starts after prepare and normally reads the completed short-lived bundle. Comments use their separate provider endpoint and also start after prepare, preventing both sections from entering the pre-prepare contention window. No arbitrary 200-500 ms delay is added because the actual prepare milestone is a more precise gate.

On a `WatchStateCache` hit:

- publish cached details, related, and comments synchronously;
- retain the active player when it already matches the key;
- otherwise start stream and resume concurrently;
- prepare when stream and bounded resume are available;
- only load missing related/comments after prepare.

Existing generation checks remain authoritative for rapid A to B to A navigation and stale non-cancellable provider work. Duplicate same-key taps retain their current no-op guard. Stream failures and unexpected exceptions must set `isLoading = false` and expose retry state.

## 7. Player Startup and Metrics

Do not alter stream selection, quality escalation, Media3 buffers, source muxing, or recovery policy in this release. Current startup selection already addresses initial quality and has targeted tests. Changing buffers without device measurements risks rebuffer regressions.

Add lightweight local timing instrumentation. It records monotonic elapsed time, event name, and non-sensitive `ContentKey` identity only in debug builds:

- `VIDEO_OPEN_START` in Watch load admission;
- `DETAILS_READY` when current-generation details publish;
- `STREAM_INFO_READY` after stream extraction succeeds;
- `PLAYER_PREPARE` immediately before controller prepare;
- `PLAYER_READY` from current-session Media3 ready state;
- `FIRST_FRAME` from current-session `AnalyticsListener.onRenderedFirstFrame()`.

Events bind to a video-open/session generation so stale sessions cannot produce misleading durations. No telemetry leaves the device. Release builds do not spam logs.

## 8. Cold Start

Stop creating `SessionPlayerController` from the application preference collector. Retain latest background-playback preference in an app-level value or provider state. When `createPlayerController()` first materializes the controller, apply current background/PiP lifecycle policy then continue normal collector updates only if a controller already exists.

`ExtractorBootstrap.init()` remains synchronous in `Application.onCreate()` so the first extractor request cannot race uninitialized global state.

## 9. Network and UI Scope

Keep current extractor network policy at connect/read/call 15/20/30 seconds and existing bounded retry behavior. Duplicate extraction and request ordering are evidenced bottlenecks; timeout reduction is not. A separate timeout change requires measured slow-network failure data.

Keep current Coil and Compose behavior. Cached Watch metadata remains visible. Related refresh retains old content. Section loading stays local to related/comments, while playback buffering remains represented by existing player state and controls.

## 10. Tests

Development follows TDD. Add focused unit tests that prove:

1. concurrent `video()`, `streamInfo()`, and `related()` for one key perform one upstream bundle extraction;
2. different keys do not deduplicate;
3. a success is reused inside 20-second TTL and re-extracted after expiry;
4. failure clears in-flight/cache state and a later request retries upstream;
5. one cancelled waiter does not break remaining waiters;
6. last-waiter cancellation cleans in-flight state;
7. stream and resume begin concurrently on fresh and cached Watch paths;
8. related and comments do not start before `playerController.prepare()`;
9. cached details render immediately without full loading;
10. errors end spinner state and retry remains deduplicated;
11. stale generations and rapid A to B to A navigation cannot prepare or publish old content;
12. duplicate same-key load does not duplicate prepare;
13. startup selection and stream recovery tests remain green;
14. cold-start preference collection does not instantiate player stack.

Run:

```text
./gradlew test
./gradlew assembleDebug
./gradlew assembleRelease
./gradlew connectedAndroidTest
```

Report `connectedAndroidTest` as unavailable, not passing, when no device/emulator is online.

## 11. Version and Signing

Update `app/build.gradle.kts`:

- `versionCode`: 4 to 5;
- `versionName`: 1.0.3 to 1.0.4;
- application ID remains `com.hpre.app`;
- release remains minified.

Use only existing `hpreSigning.*` Gradle properties or `HPRE_SIGNING_*` environment variables. Never generate a key or alias. Build must stop if any signing input is missing or configured keystore does not exist.

Rename final signed release APK to `HPre-v1.0.4.apk`. Verify with Android build tools:

- APK signature validity;
- package `com.hpre.app`;
- `versionName` 1.0.4;
- `versionCode` 5;
- signer SHA-256 certificate.

Use official HPre 1.0.3 release APK as baseline. The candidate and baseline signer SHA-256 values must match. If a device becomes available, run the repository upgrade gate to install baseline, write its DataStore marker, install candidate with `adb install -r`, and verify marker/settings persistence. A certificate mismatch, install-over failure, or signing ambiguity blocks push and release.

## 12. Git and GitHub Delivery

Work on `perf/hpre-1.0.4`. Before commit, inspect status/diff, run `git diff --check`, and ensure no keystore, secrets, `local.properties`, or unnecessary build output is staged.

After all local push gates pass, commit implementation as:

```text
perf: optimize playback startup and release 1.0.4
```

Push branch and create a PR into `main`. Do not merge it automatically. Because existing HPre release tags point to `main`, stop before creating `v1.0.4` until the user merges the PR.

After merge confirmation, verify merged commit, create and push tag `v1.0.4`, then create GitHub Release `HPre v1.0.4` and attach only `HPre-v1.0.4.apk`. Release tooling may require installation/authentication of GitHub CLI; credentials must never appear in source, command output, or release assets.

## 13. Acceptance Criteria

The implementation is ready for PR when:

1. one video-open burst performs at most one expensive upstream stream-page extraction per key;
2. short bundle cache is bounded, TTL-limited, thread-safe, failure-cleaning, and waiter-cancellation-safe;
3. cached Watch details appear immediately;
4. stream extraction and resume lookup are concurrent on both fresh and cached paths;
5. related/comments do not enter the path before `playerController.prepare()`;
6. every loading path terminates in content, error, or cancellation;
7. existing player selection, recovery, UI, cache, and persistence tests remain green;
8. debug timing can report tap-to-details, tap-to-stream, tap-to-prepare, tap-to-ready, and tap-to-first-frame;
9. unit tests, debug build, release build, package/version checks, signature verification, and baseline certificate comparison pass;
10. unavailable device checks are reported accurately.

Release is complete only after the PR is merged, tag and GitHub Release exist, signed APK asset is downloadable, and all required signing checks remain valid.

## 14. Deliberate Omissions

- Network timeout tuning is skipped until measured failures show timeout, rather than duplicate extraction, dominates waiting.
- Media3 buffer tuning is skipped until device rebuffer and first-frame measurements justify a safe value.
- New benchmark module is skipped; debug timing and focused deterministic tests cover this release. Add a benchmark module only when repeatable device baselines require it.
- General cache abstraction is skipped; one short-lived bundle cache is enough for known duplicate work.
